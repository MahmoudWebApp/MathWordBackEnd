# R1 recovery and transactional mail (not activated)
- Provider: Brevo HTTPS API, endpoint fixed to api.brevo.com/v3/smtp/email. Existing manual SMTP announcements are unchanged.
- Required environment variables on backend only:
  - `MathWorldEmail__Brevo__Enabled=true`
  - `MathWorldEmail__Brevo__ApiKey` (secret)
  - `MathWorldEmail__Brevo__From` (verified sender)
  - `MathWorldEmail__Brevo__Mode=test`
  - `MathWorldEmail__Brevo__TestRecipients` (semicolon-separated verified test addresses)
  - `MathWorldEmail__OutboxEnabled=true`
  - `MathWorldRecovery__Enabled=true`
  - `MathWorldRecovery__TokenKey` (independent cryptographically random >=32 bytes, Base64; never commit)
  - `MathWorldRecovery__VerifiedAdminEmail` (explicitly verified existing administrator address, not guessed)
  - `MathWorldBrand__WebsiteUrl` only if the official website changes.
- Keep all flags off until backend + web recovery paths are ready. Disable provider click/open tracking for account recovery; do not collect or forward recovery URLs. Test sending requires test mode, current admin's own allowlisted address, and worker enabled; no automatic send occurs on deployment.
- Password recovery requests are generic. Existing local-only students prove control by redeeming the mailbox link; no claim of historical email verification. Staff email must be explicitly verified before allowing recovery. Existing linked Google/social accounts sign in via provider until their verified-email/link ownership migration is reviewed; the database historically does not distinguish Google-only accounts from local accounts later linked to Google. Do not silently add a local login or allow an unverified linked identity to survive a recovery flow.
- DB stores SHA-256 digests, not plaintext tokens; a separate server key derives a short-lived secret from random grant IDs for the worker. Rotate the recovery key only after outstanding grants expire or explicitly invalidate them.
- Outbox acceptance is not delivery. Retries only on explicit provider 429; ambiguous network or 5xx outcomes become Unknown, not automatically replayed. Max three attempts, 20-minute grant expiry, durable claim/lease, conservative 100-attempt default rolling-overlap cap with priority for recovery. Admin status excludes recipients, secrets and rendered messages.
- Delivery/bounce webhooks, verified-link account migration, real provider activation, user-facing browser/device smoke and launch acceptance remain separate checks. Do not enable live mode until verified.

Admin outbox readiness now reports missing configuration codes (never values), whether an allowlisted administrator can enqueue a test under the reserved budget, and whether admin recovery is locally configured. Provider connection and inbox delivery remain explicitly unverified; a real test must still be sent and checked. The disposable password suite asserts that configured transport with disabled worker cannot be reported ready for testing or admin recovery, and that the response contains no test key or address. No production env changes.

All ten bilingual preview/test variants now share one fixed sample catalog and the existing common header/footer. Test requests accept an allowlisted template, never include a live token, and share the original global/per-admin limit across variants. Queued samples remain blocked in live mode. Certificate issue now atomically creates a single in-app notice, including replay protection. No automatic non-security email to learners is enabled: verified recipient identity and preferences, real provider setup, delivery/bounce tracking and inbox confirmation remain gates. No production sending or configuration changes.

Optional event delivery: additive preferences and verified address fields default to off/unverified. Successful mailbox reset records the exact verified address; no historical address or linked Google account is silently treated as verified. Student-only read/write API stores language and three opt-ins. Certificate issue, admin Premium grants/renewals and single-learner in-app notices enqueue generic mail in the same database save when explicitly enabled, with fresh eligibility checks before delivery. `MathWorldEmail__OptionalEventsEnabled` defaults off. Bulk announcements, legacy SMTP, welcome/verification, scheduled expiration events, client settings and actual provider delivery require separate acceptance; no actual emails sent by this change.

Premium gift redemption and the existing dormant verified payment settlement now queue the same optional subscription templates in their transactions; no payment activation. The new expiry worker is separately disabled by default (`MathWorldNotifications__PremiumExpiryEnabled`), uses the existing per-user subscription lock and persists one notice marker per expiry timestamp, without changing entitlements. It handles expiries within a 48-hour catch-up window; older terms are intentionally not replayed on activation. Optional email still requires verified address, opt-in, enabled worker/provider and delivery checks. Disposable CI covers repeated sweeps and renewed terms with email disabled.

CI-only optional event queue test now explicitly enables the test-mode offline path while the worker remains disabled. Tests cover unverified opt-in rejection, verified consent, queueing of individual announcements and single-use Premium gift redemption, and later opt-out. Public preference readiness requires configured/allowlisted transport and enabled worker; flags alone do not imply delivery readiness.

Separate mailbox confirmation is now implemented using `EmailVerificationGrants`, a purpose-separated HMAC and independent one-use token, with explicit authenticated learner request and anonymous POST confirmation from an official fragment link. It never resets a password, links Google, signs in, changes roles or grants optional consent. Existing local and Google-linked learners can request a welcome/verification email to their exact account address. `MathWorldEmail__VerificationEnabled` defaults off; delivery is disabled until sender setup. Request cooldown two minutes, 30/day default cap, 20-minute grant expiry, private RLS table and atomic consumption. Offline CI verifies only; no provider requests. Registration does not automatically send a message; existing and new users may request it in settings. Automatic registration onboarding remains separate.

Registration welcome is now automatically queued for newly created local or Google student accounts, after the account transaction commits, via `MathWorldEmail__WelcomeOnRegistrationEnabled` (default off). The same independent verification service, exact address, per-account cooldown and global caps apply. Existing Google logins do not send welcome repeatedly. Queue failure does not fail registration or sign-in; the user can retry from settings. No external provider call takes place in the request. Offline CI covers registration queueing and subsequent reissue after password change; live Google and inbox delivery still need acceptance.
